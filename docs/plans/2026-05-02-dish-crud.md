# Plan: proper CRUD on the dish API

Roadmap item `-pkyaaXLbLV3` ("Add proper CRUD to the dish api"). Two
goals from the user:

1. Make it possible to **update** dishes — currently the `PATCH
   /api/dishes/[id]` route exists but validates the body with
   `DishInputSchema`, which requires `title` and `baseServings`. So in
   practice it's a full-replace (PUT-shaped) endpoint, not a real PATCH.
   You can't tweak just a tag or just the favorite flag without
   re-sending the entire dish.
2. Make Nex aware of the update endpoint — the only registered tool on
   the claude-agent dashboard is `dinner_spinner_add_recipe` (POST).
   There's no way to update or delete a dish through Nex's tool layer.

## Decisions (autonomous, calling these myself)

- **PATCH semantics → real partial updates.** Validate the body against
  `DishInputSchema.partial()`. Fetch the existing row, merge the
  provided fields in JS (using `=== undefined` so an explicit `null`
  still clears a nullable field), then write the merged record back. No
  dynamic SQL — it's a single dish, easier to reason about, and the
  cost of fetching the row before writing is irrelevant for this app.
- **Empty body → 400.** Refusing no-op PATCHes is friendlier than a
  silent success.
- **Existing admin UI still works.** It currently sends the full
  payload as PATCH; that's a valid subset of "any partial body", so no
  client changes needed.
- **Apply pantry defaults only when `ingredients` is in the payload.**
  Otherwise we'd have to refetch and re-process the existing
  ingredients, and `applyPantryDefaults` is idempotent on already-saved
  rows so there's no benefit.
- **Nex tools to add:** `dinner_spinner_update_recipe` (PATCH) and
  `dinner_spinner_delete_recipe` (DELETE). Read endpoints are already
  reachable by curl without auth, so no list/get tool is needed for
  CRUD coverage. (The user explicitly asked for the PATCH tool. Adding
  delete alongside is cheap and rounds out the auth-required surface.)
- **No test framework added.** Project has zero existing tests and
  introducing vitest/node:test for a 30-line handler change is
  over-engineering. Verification plan: `npm run build` + manual curl
  against a dev server hitting a scratch dish, covering each partial
  update shape. Documented as a trade-off here so future-me can revisit
  if test infra arrives.

## Implementation

### 1. `lib/types.ts`

Add `DishPatchSchema = DishInputSchema.partial()` and export
`DishPatchInput` type. Keep `DishInputSchema` as-is (POST still
requires the full body).

### 2. `app/api/dishes/[id]/route.ts` PATCH handler

Replace the body of PATCH with:

```ts
const parsed = DishPatchSchema.safeParse(body);
if (!parsed.success) { /* 400 */ }
if (Object.keys(parsed.data).length === 0) {
  return Response.json({ error: "No fields to update" }, { status: 400 });
}

const existingRows = await sql`SELECT * FROM dishes WHERE id = ${Number(id)}`;
if (existingRows.length === 0) { /* 404 */ }
const existing = rowToDish(existingRows[0]);

const u = parsed.data;
const ingredients = u.ingredients !== undefined
  ? await applyPantryDefaults(u.ingredients)
  : existing.ingredients;

const merged = {
  title:        u.title        ?? existing.title,
  subtitle:     u.subtitle     === undefined ? existing.subtitle     : u.subtitle,
  recipe:       u.recipe       === undefined ? existing.recipe       : u.recipe,
  tags:         u.tags         ?? existing.tags,
  baseServings: u.baseServings ?? existing.baseServings,
  favorite:     u.favorite     === undefined ? existing.favorite     : u.favorite,
  imageUrl:     u.imageUrl     === undefined ? existing.imageUrl     : u.imageUrl,
  emoji:        u.emoji        === undefined ? existing.emoji        : u.emoji,
  accent:       u.accent       === undefined ? existing.accent       : u.accent,
  notes:        u.notes        === undefined ? existing.notes        : u.notes,
};
```

Then UPDATE with the merged record (same column list as today, just
sourced from `merged` + `ingredients` instead of straight `parsed.data`).

`title` and `baseServings` use `??` because they're non-nullable; the
others use the `=== undefined` form so explicit `null` clears them.

### 3. Nex dynamic tools

Append two entries to `~/claude-agent/data/dynamic-tools.json`:

- **`dinner_spinner_update_recipe`** — args `{ id: number, patch: string }`
  where `patch` is a JSON string of any subset of dish fields. Handler:
  `curl -sS -X PATCH .../api/dishes/$ID -H "Authorization: Bearer
  $DINNER_SPINNER_API_TOKEN" -d "$PATCH"`.
- **`dinner_spinner_delete_recipe`** — args `{ id: number }`. Handler:
  `curl -sS -X DELETE .../api/dishes/$ID -H "Authorization: Bearer
  $DINNER_SPINNER_API_TOKEN"`.

Both reuse the existing `DINNER_SPINNER_API_TOKEN` envAllowlist entry.

After editing the JSON, `pm2 restart claude-agent` so the dashboard
re-reads it.

### 4. Verification

Against a local dev server pointing at the prod DB (or a scratch dish):

1. `POST /api/dishes` to create a fresh test dish, capture id.
2. `PATCH /api/dishes/:id` with `{"favorite": true}` → expect 200,
   favorite flips, all other fields unchanged.
3. `PATCH /api/dishes/:id` with `{"title": "Renamed", "tags":
   ["foo"]}` → expect 200, only those fields changed.
4. `PATCH /api/dishes/:id` with `{"subtitle": null}` → expect subtitle
   cleared (the `=== undefined` distinction).
5. `PATCH /api/dishes/:id` with `{}` → expect 400.
6. `PATCH /api/dishes/:id` without auth → expect 401.
7. `PATCH /api/dishes/99999` with valid body → expect 404.
8. `DELETE /api/dishes/:id` → cleanup.
9. After deploy: re-run #2/#3 against prod URL with the real token.
